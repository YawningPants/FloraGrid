# 日枝：花朵与花田的性能评估、设计建议

## 结论

改动前静置的日枝进程组没有显著持续 CPU 占用，私有驻留内存约 102.5 MiB。主要风险是高任务量下完成操作的整列表重建，以及旧花田预览对大量 SVG 和隐藏视图的重复创建。已实现的开花与局部更新复测见第十节，随机花型与曲枝版本复测见第十一节；花田仍只保留设计探索。

建议采用两种方式配合：日任务完成用少量自定义 SVG 与局部动画；月、年花田用 Canvas 2D 绘制缓存花朵，按视图层级控制密度。年概览显示花簇和准确数量，进入月份/日期再逐朵显示。

花型、密度和渲染器分别处理。换成 Canvas 本身不会解决拥挤成块的视觉问题。

## 一、测试条件和边界

- 本机 CPU：AMD Ryzen 7 9700X，16 个逻辑处理器；Windows 可用物理内存约 31.1 GiB。
- 图形测试设备：NVIDIA GeForce RTX 5070，ANGLE / Direct3D 11。
- 正在运行的原生日枝为 debug 构建，WebView2 155.0.4283.62。
- 前端压力样本使用独立的 Chrome 155.0.8059.85，1180 × 820 视口，DPR 2。
- 没有操作实际任务内容。原生部分仅查询进程资源；前端样本使用临时浏览器目录和虚构任务。
- 每个构建场景预热后测 5 次，表格列中位数。5 个样本不足以代表长期尾部表现。
- 耗时包含同步 JavaScript、样式/布局提交，不等于完整 GPU 绘制时间。
- 前端压力结果不替代正式版 WebView2、多窗口、低配设备和真实桌面透明合成的验收。
- 数值见 [measurements.json](measurements.json)。不将 JavaScript 堆大小当作整个应用的 RAM。

## 二、正在运行的原生应用：静置采样

| 指标 | 观察值 |
| --- | ---: |
| 私有驻留内存 | 102.5 MiB |
| 私有提交内存 | 约 213.8 MiB |
| 进程组工作集相加 | 约 394 MiB |
| CPU | 五个约两秒区间内，整机归一化 CPU 增量均舍入为 0.000% |

工作集包含共享页，跨进程求和会重复计算；394 MiB 不能理解为软件独占了这些物理内存。私有提交也不等同于当前物理驻留内存。

采样没有控制用户窗口的可见性和数量，不能据此断言任意多窗口场景都拥有相同占用，也不能将短时间的 0.000% 写成“零 CPU”。

## 三、改动前日视图基线：实际执行完成操作

| 样本 | 页面元素数 | 完成一次的中位耗时 |
| --- | ---: | ---: |
| 50 项任务 | 1,503 | 12.1 ms |
| 200 个顶层任务及子任务，共 300 项 | 9,353 | 78.1 ms |
| 500 个顶层任务及子任务，共 750 项 | 23,378 | 291.5 ms |

这些是隔离 Chrome 中运行改动前真实前端代码的结果。测试选择可完成的叶子任务，并验证完成数确实增加，避免误测“父任务还有未完成子项”的阻止提示。

大样本同时包含标签、继承标签和展开的子任务，不能只凭条目数推广到所有用户数据。

代码中的相关成本：

1. 完成操作会调用整个日视图的重建，标题、工具栏和任务区都会重新创建。
2. 新任务节点包含操作按钮、图标、标签、树枝等，元素数量随任务量增长。
3. 树枝与继承标签排版会读取几何位置，并写入样式；重建之后还会排队执行布局。
4. 自动保存会制作任务树快照。这个成本需要与布局成本分开分析。

优化顺序：

- 先更新完成按钮、卡片状态、统计数字和受影响的父子分支。
- 保留现有任务数据与拖拽规则，减少无关节点替换。
- 将几何读取集中进行，再统一写样式；只测量需要变化的可见分支。
- 花开完成后再安排卡片的排序移动，保持反馈可见。
- 数百条展开任务的视口化，作为后续独立优化验证，避免和视觉改造一次性混在一起。

## 四、统一简化花型的渲染比较

以下均为同一 760 × 360 画面、DPR 2、相同尺寸花头，强制构建/布局后的主线程提交耗时。此处是渲染器压力样本，不是最终的花田排版。

| 方式 | 1,000 朵 | 5,000 朵 | 5,000 朵公开页面元素数 |
| --- | ---: | ---: | ---: |
| 每朵完整 SVG | 20.7 ms | 135.7 ms | 40,000 |
| SVG symbol/use | 21.1 ms | 129.3 ms | 5,010 |
| 每朵一张、共享同一图像的 img | 9.4 ms | 50.8 ms | 5,000 |
| Canvas 逐朵执行矢量绘制 | 4.7 ms | 29.0 ms | 1 |
| Canvas 绘制已缓存图像 | 0.8 ms | 6.3 ms | 1 |

注意：

- SVG use 的公开 DOM 少，但浏览器仍维护实例渲染树。这个样本中，包含内部实例的 DOM 计数约五万，耗时也没有随公开元素数成比例下降。
- Canvas 数据和图像缓冲并非免费。760 × 360、DPR 2 的单份 RGBA 像素缓冲约 4.17 MiB；实际还可能有纹理、缓存、双缓冲等开销。
- 美观细节可以预先画入小图。缓存后每朵重复使用同一个图像，不需要每次重算渐变、曲线和花瓣。
- 三种自定义花型的缓存可以按当前主题懒加载，不用一次预载所有主题和全部动效帧。

### 局部动画样本

36 个简化 SVG 中仅对 1、3、12 朵做 420 ms 的缩放、旋转和透明度动画，独立测试的 P95 帧间隔约 16.8 ms，未观察到大于 25 ms 的帧间隔。

它支持“少量局部动效可行”的判断，不代表已经验证了原生应用中同时重建大列表的体验。正式实现应将局部动画和整列表重建解耦。

## 五、旧预览为何需要替换

| 年记录规模 | 旧预览页面元素数 | 点击一次完成的中位耗时 |
| --- | ---: | ---: |
| 约 100 | 2,080 | 7.9 ms |
| 约 1,000 | 13,569 | 48.0 ms |
| 约 5,000 | 66,769 | 213.7 ms |

测试点击会增加或撤回一个样本记录，规模有一项波动。

旧预览每次操作都重建月、年两套花田，包括隐藏视图，并逐项转换图标。应改为只更新当前可见视图，仅在数据、主题、尺寸、缩放或选中状态改变时绘制。

视觉方面，通用线图标整体填白、缩至几像素、花头与相邻花重叠，使花朵失去花心和花瓣间隙。这需要重新设计花型与尺度，不能只换渲染器。

## 六、新的视觉方案

### 花型

- 五瓣小野花：花瓣轮廓清楚，低饱和奶油色，适合 18 px 完成图标，建议作为默认。
- 细瓣小雏菊：更轻、更温暖，较适合花田；小尺寸需要控制细节。
- 重瓣小山茶：柔和的灰粉色，适合雾玫灰等主题；图标版使用简化层次。

这次使用独立设计的曲线/花瓣，没有继续将通用图标填成白色。花田版可用细节更多的缓存贴图，完成按钮用同一花型的简化矢量版。

### 年视图的密度

- 概览用十二个月份分区，同一缩放下采用统一的花簇计量单位。
- 每个月最多约 24 个花簇，月份之间仍然表现数量差异，真实完成总数用文字显示。
- 点击月份后绘制该月的每一朵；数量更多时再缩放、平移或进入日期详情。
- 数据完整保留，概览聚合不删除记录。图例必须明确花簇与逐朵两种口径。
- 保留负空间和最小花头间距，使用轻微、稳定的姿态和落点差异。
- 用户如希望全年所有花同时存在于一个大场景，可采用可缩放大花田及视口绘制；它应有自己的交互设计，不能再压成一页微缩图。

### 新预览检查

使用 5,000 条示例记录：

- 年花田区域约 50 个页面元素，花朵由一个 Canvas 绘制。
- 年概览在此示例尺寸的有色像素约占 4%，检查了留白，避免连成色块。
- 年概览重建的 5 次样本中位数约 1.6 ms；这里实际画的是花簇，不能称为“绘制 5,000 朵只要 1.6 ms”。
- 进入十月后逐朵显示该月的 550 项示例记录。
- 三种花型、420 ms 开花重播、月年切换及窄窗口排版通过概念检查。

## 七、给这个项目建议的性能预算

这些是建议的验收目标，不是所有桌面软件的通用标准，也不是本次已完成原生实现的承诺。

| 项目 | 建议目标 |
| --- | --- |
| 花功能新增私有驻留内存 | 常用场景尽量控制在约 10～20 MiB，原生发布版实测确认 |
| 静置 | 不运行花朵动画循环；完成动效结束后停止 RAF |
| 单次开花的新增脚本工作 | 争取低于 2 ms；不触发全列表重新排版 |
| 动画 | 以 60 Hz 的约 16.7 ms 帧预算设计，减少动态效果模式直接切换静态状态 |
| 年概览首次构建 | 主线程尽量低于 20 ms；高密度数据分层、缓存或分帧 |
| 交互 | 悬停只重画高亮；利用位置索引命中，不重建整座花田 |
| 像素与纹理 | 控制 DPR，避免无限大画布；按可见区域绘制，退出视图可释放重缓存 |
| 多窗口 | 复用月视图中的花田页面，不为花田额外开一个常驻 WebView |

不增加持续摇摆、逐朵模糊、实时光影、3D 物理模拟等常驻工作。精致的花型可以来自小尺寸的预绘图像，视觉质量与每帧计算量可以分开控制。

## 八、实施顺序

1. 先收敛日任务完成时的重建范围，保留现有状态、复制、父子任务和拖拽规则。
2. 选择花型，制作图标版和缓存图像版，接入一次性的局部开花。
3. 补完成时间与花田统计口径，再实现月花田和有明确图例的年概览。
4. 在正式版 WebView2 的常用窗口、多窗口、1,000/5,000 条记录下复测；至少补一个普通集显设备验证。

## 十、开花接入后复测（2026-10-24）

日枝外观、开花开启；同一台机器、Chrome 155、1180 × 820、DPR 2；每组预热后五次叶子任务完成。原始记录见 [completion-2026-10-24.json](completion-2026-10-24.json)。本轮没有实现花田，也没有重测原生私有驻留内存，不能将前述 102.5 MiB 视为改动后的内存。

| 任务数 | 点击同步响应中位数 | 完整周期累计 Script | 累计 Style/Layout | 累计 Task | 单次周期帧间隔 p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 50 | 1.5 ms | 1.5 ms | 3.6 ms | 16.9 ms | 16.8 ms |
| 300（含子任务） | 2.9 ms | 3.2 ms | 4.8 ms | 37.2 ms | 16.8 ms |
| 750（含子任务） | 4.5 ms | 5.4 ms | 7.7 ms | 67.8 ms | 16.8 ms |

点击响应是状态改变、局部 DOM 更新及同步样式/布局提交；不能把它理解为开花和排序的总开销。完整周期采用点击后 800 ms 的观察窗口，覆盖约 420 ms 开花和 220 ms 归位。累计 Task 包含该窗口内脚本、渲染等主线程工作，分散在多帧执行，不等于一次连续阻塞 67.8 ms；也不等于 GPU 总耗时。每组另采一个完成周期的帧间隔，三个样本均未出现超过 25 ms 的帧，但样本量不足以代表长期尾部表现。

实现采用一次性小 SVG、局部任务行替换、只移动变更任务、批量布局读取和跳过无变化的枝线写入。只为视口附近需要归位的卡片做 transform 动画；精简外观不创建花朵 SVG。没有新增持续 RAF 或额外 WebView。

这批隔离前端样本支持当前轻量方案；发布前仍应在正式版 WebView2、真实桌面透明合成和普通集显设备上验收。新流程把反馈和排序分成两个阶段，因此不能仅拿改动前同步耗时除以新点击耗时，宣传为完整操作的加速倍数。

## 十一、六种花型与曲枝接入后复测（2026-10-24）

本轮加入任务花型/花色元数据、每个父子分组一个静态 SVG，以及月历一个静态 SVG。相同脚本和采样口径下，重新测试日视图的叶子任务完成；这里不包含父任务自动折叠的额外 280 ms 视觉时长。原始记录见 [branches-2026-10-24.json](branches-2026-10-24.json)。

| 任务数 | 点击同步响应中位数 | 完整周期累计 Script | 累计 Style/Layout | 累计 Task | 单次周期帧间隔 p95 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 50 | 1.6 ms | 1.4 ms | 3.8 ms | 15.8 ms | 16.8 ms |
| 300（含子任务） | 2.6 ms | 3.5 ms | 4.8 ms | 33.4 ms | 16.9 ms |
| 750（含子任务） | 4.1 ms | 6.7 ms | 8.0 ms | 68.2 ms | 16.8 ms |

三组另采的完成周期都未出现超过 25 ms 的帧，未记录运行时异常。与第一版相比没有观察到明显交互回退，但五次样本不能证明各种机器均无卡顿；不同采样的微小差异不应解释为确定的性能提升。

枝条仅在布局、拖拽预览、折叠起止或月历尺寸变化时更新。布局测量先集中读取，再写入 SVG；无变化的路径不重建。没有新增静置动画或额外 WebView。月历属于静态布局，本轮通过界面与尺寸回归验收，未另行采集原生 GPU、内存或多窗口功耗。父任务折叠通过实际中间高度的专项浏览器检查。
