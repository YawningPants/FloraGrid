# 日视图花丛性能评估

日期：2026-10-25。原始样本：[header-garden-2026-10-25.json](header-garden-2026-10-25.json)。

## 结论

下文首先保留加入花丛时的基线。本文末尾的“本轮优化复测”包含最新的后台暂停、交互优化及原生发布版内存数据，应以该节判断当前版本。

当前花丛的结构、脚本与内存增量较小，持续摇曳带来了可测量的常驻图形合成开销。正常窗口在本机保持流畅，但不能将它描述为“零 CPU”或仅凭 60 FPS 判断省电。任务量增加时，整体任务列表的 DOM、快照保存和排序布局仍然是主要的规模风险。

本轮已经增加备用生长位置：320px、390px、宽窗口分别显示最多 6、8、12 株，提供 9、12、16 个候选位置。新花避开退场花的位置，现有花保持不动。备用位置是坐标，没有预先创建植株。

## 测试方法与边界

- 本机 16 个逻辑处理器；Chrome 155 独立临时用户目录，真实应用前端；DPR 2，常规视口 390×900，另测 600×900 的 12 株花。
- 50、300、750 项虚构任务，包含展开子任务、标签与不同状态。没有读取或修改真实日历数据。
- 三种模式：HTTP 测试服务器仅将花丛控制器替换为空实现的基线；真实花丛关闭摇曳的静态样本；完整花丛与摇曳。静态样本只用于隔离摇曳成本，没有新增产品设置。
- 浏览器先预热 8 秒；每次完整重载，禁用历史页面缓存。GC 后每个样本仅保留 1 个文档，避免旧页面污染堆内存对比。
- 每种模式采两段 3 秒静置数据。静置期间不使用 RAF 探针，帧间隔另行采样。
- 完成操作先预热一次，再测 4 次；每次观察 1,600ms，覆盖任务盛开、缩小、排序和背景花生长。另测 6 次、间隔 70ms 的连续完成。
- 当前未运行日枝原生进程；本轮未测 WebView2 发布版的进程 RAM、GPU 引擎利用率、桌面透明合成、多窗口和电池功耗。

## 单次完成任务

单位 ms，中位数：

| 任务数 | 无花丛：点击同步工作 | 完整花丛：点击同步工作 | 新增同步工作 | 无花丛：1.6秒内累计主线程 Task | 花丛：1.6秒内累计主线程 Task |
| ------ | -------------------: | ---------------------: | -----------: | -----------------------------: | ---------------------------: |
| 50     |                 1.60 |                   2.60 |         1.00 |                          50.82 |                       109.90 |
| 300    |                 2.20 |                   4.00 |         1.80 |                         101.86 |                       160.01 |
| 750    |                 3.45 |                   7.10 |         3.65 |                         179.35 |                       248.59 |

同步工作包括事件处理、状态与 DOM 更新以及强制样式/布局提交，不是动画总时长，也不是第一次像素呈现的延迟。右两列是分散在 1.6 秒内的累计工作量，不能解释成一次连续阻塞 249ms。

完整花丛在 50、300、750 项的完成周期中，累计 Script 中位数分别约 5.01、9.54、17.20ms；累计 Style/Layout 分别约 19.74、23.51、32.80ms。剩余 Task 时间还包含绘制等主线程工作。

静置帧间隔 P95 为 16.8–16.9ms，单次完成与连续完成样本约 16.8ms，本轮未观察到超过 25ms 的帧间隔。短样本不代表低配机器或长期尾部表现。

## 持续摇曳的 CPU

以下为 **renderer + GPU 进程的 CPU 时间**，按单个逻辑处理器计 100%。GPU 进程 CPU 时间不是显卡 GPU 使用率。

| 任务数 | 无花丛 | 静态花丛 | 持续摇曳 | 摇曳折合本机整机 CPU |
| ------ | -----: | -------: | -------: | -------------------: |
| 50     |  0.22% |    0.78% |    8.56% |                0.54% |
| 300    |  0.43% |    0.20% |    8.77% |                0.55% |
| 750    |  0.15% |    0.27% |    8.80% |                0.55% |

差异较小的静态/关闭样本存在后台 housekeeping、GC 等短采样噪声，不能声称静态花丛让 CPU 下降。原始记录保留了整浏览器进程组 CPU 和各进程类型时间；首个无花丛样本的 browser/network 进程有明显后台工作，因此没有将整浏览器 CPU 直接归因于花丛。

- 常规窗口摇曳开销与 50→750 项任务量基本无关，因为仅有 8 株、3 组摇曳。
- 750 项、600px 宽、12 株样本的整个隔离浏览器进程组约占单核 9.29%，折合本机整机 0.58%（单段 3 秒）。
- 750 项窗口失焦后，摇曳暂停；整个隔离浏览器进程组约占单核 0.41%，折合整机 0.026%（单段 3 秒）。
- 摇曳时主线程 Task 约 0.4–0.46ms/秒；静置 Script 样本为 0。常驻成本主要在渲染线程和图形合成，不是持续执行 JavaScript 来重新计算叶片。

## 结构与内存

| 任务数 | 无花丛页面元素 | 花丛新增元素 | 无花丛 JS 堆 | 完整花丛 JS 堆 |
| ------ | -------------: | -----------: | -----------: | -------------: |
| 50     |          1,678 |       约 211 |     1.15 MiB |       1.29 MiB |
| 300    |          9,988 |       约 229 |     1.33 MiB |       1.48 MiB |
| 750    |         24,690 |       约 191 |     1.73 MiB |       1.99 MiB |

花型不同导致 SVG 节点数有少量差异。宽窗口 12 株样本约 296 个花丛元素；它不会随已完成任务数无限增长。另一个 750 项全完成回归样本为 332 个花丛元素，差异来自样本花型。

JS 堆增量约 0.1–0.3 MiB，**不是花丛的总 RAM 增量**。该数值不包含 DOM 底层、纹理、遮罩缓存、合成缓冲、WebView2 运行时及 Tauri 原生进程，不能用来宣称整个软件只占几 MiB。

## 代码分析与后续优化顺序

已经控制的部分：

1. 可见植株上限与备用坐标分离。每株 4–7 片叶子合并为两条路径，没有逐叶节点、滤镜或独立动画。
2. 形态由任务 ID 稳定生成并缓存；几何没有变化就不重建枝叶。文字遮罩也只在区域变化时更新。
3. 背景只有一个 SVG 和三组摇曳；出入场同时最多两株，快速操作不会积累动画队列。
4. 失焦、隐藏、最小化时暂停；空白日期没有背景动画。关闭动态效果时直接使用静态状态。

接下来更值得处理的成本：

1. **省电优先处理持续摇曳。** 可将“背景摇曳”与一次性完成反馈拆成独立设置，或改成间歇微风。当前动画开关同时影响完成反馈，本轮没有修改这一产品行为。
2. **高任务量优先处理列表规模。** 当前 750 项已经有约 2.5 万个元素，列表未做视口化。完成后的排序/枝线布局会访问同级节点和子任务容器。视口化需要同时保护拖拽、搜索定位和枝线连续性，应作为独立改动验证。
3. **减少编辑与保存的重复快照。** `getPersistableTasks` 先复制任务树，`scheduleSaveDay` 再做 `structuredClone`。保存虽然有 900ms 防抖，这两次制作快照仍会在操作时同步发生；任务多时应优先减少重复复制。
4. 正式发行前补测发布版 WebView2 的总进程资源、集显、高 DPI 和多窗口。Chrome 的短期帧率不能替代这些验收。

## 本轮优化复测

原始结果：[前端优化后样本](header-garden-optimized-2026-10-25.json)、[原生后台样本](native-background-2026-10-25.json)。

### 后台停止动画

发现并修复了两个遗漏：

- 页面失焦时，原来只暂停花丛摇曳，尚未结束的生长、淡出、任务完成和折叠反馈仍可能继续。现在后台直接收束有限动效，取消折叠 RAF、任务归位动画和拖拽，并保留已经提交的状态；恢复时不重播旧反馈。
- Windows 上的隐藏 WebView 可以将 DOM 可见性报告为 `visible`。现在同时读取原生窗口 `isFocused / isMinimized / isVisible`，监听原生焦点和尺寸事件，以真实窗口状态为准，并使用序号忽略过期的异步查询。

优化后的 750 项 Chrome 样本：整浏览器进程组 CPU 从前台约 0.547% 降到失焦后的 0.034%（本机 16 线程归一化），短采样约降低 94%。原生隐藏窗口确认 `nativeVisible=false`、`nativeFocused=false`，三个摇曳动画均为 paused；约 3.5 秒区间未分辨出 CPU 时间增量。它们都不代表软件长期“零 CPU”，保存与日期/提醒检查仍会按需工作。

暂停主要节省 CPU、图形合成和功耗，不会自动释放整个 WebView、任务 DOM 和已有纹理缓存，因此不应预期内存同比例下降。

### 已实施的优化

1. 删除保存前多余的一次全任务树深拷贝。空草稿过滤采用结构共享，只有被剪枝的祖先需要新对象；存储队列仍同步制作一份独立深快照，后续编辑不能改变排队数据。补测了嵌套元数据隔离、写入失败和重试。
2. 花丛几何仅在顶部结构或尺寸变化时测量，查询限制在顶部区域；未变化植株直接跳过几何生成、花型字符串和 DOM 写入。布局观察回调复用已计算的候选集合。
3. 完成/撤销完成时直接增量更新统计数字，不重新遍历任务树和替换整组统计节点。
4. 完成后的枝线测量限定为变更节点自己的子任务容器及祖先分支，避免重新读取所有无关任务分组。
5. Windows 发布版以 GUI 子系统启动，去掉额外的控制台与 conhost 进程；开发版继续保留诊断控制台。

### 优化前后交互

相同虚构任务、视口、DPR 和 1,600ms 观察窗口，预热后 4 次样本的中位数：

| 任务数 | 优化前点击同步工作 | 优化后点击同步工作 | 优化前周期累计 Task | 优化后周期累计 Task |
| ------ | -----------------: | -----------------: | ------------------: | ------------------: |
| 50     |             2.60ms |             2.45ms |            109.90ms |            118.32ms |
| 300    |             4.00ms |             2.90ms |            160.01ms |            157.25ms |
| 750    |             7.10ms |             3.90ms |            248.59ms |            239.61ms |

750 项同步工作约减少 45%；这不是完整动画周期或整个软件提速 45%。50 项的小差异和累计 Task 波动不足以证明整体收益。新花生长与持续摇曳的绘制风格保留，因此其绘制开销仍然存在。连续完成样本仍保持约 16.8ms 的帧间隔 P95，本轮未出现超过 25ms 的帧。

本轮没有观察到前台持续摇曳的显著省电收益。它仍有约 0.5–0.7% 的整机 CPU 常驻成本（本机 16 线程，短采样）；暂停后台的收益远大于小幅减少静态 SVG 节点。

### 原生发布版：后台内存

使用同代码的 release 性能样本、全新应用标识、单个配置为隐藏的 390×900 窗口、独立虚构数据和 WebView2 诊断端口。未访问真实日历目录。采样后关闭样本并清理独立配置；原有 release 可执行文件已恢复并核对哈希。

| 场景                   | 进程组私有驻留内存 | 私有提交内存 | 工作集简单相加 | 后台 CPU 短采样 |
| ---------------------- | -----------------: | -----------: | -------------: | --------------- |
| 50 项任务、8 株花      |          107.9 MiB |    285.5 MiB |      399.1 MiB | 未分辨出增量    |
| 750 项全部展开、8 株花 |          203.9 MiB |    450.1 MiB |      501.4 MiB | 未分辨出增量    |

私有驻留内存来自 Windows 进程性能计数器，包含样本及其 WebView2 子进程；提交量不等于物理 RAM。工作集求和包含重复共享页，不能把 501MiB 当成软件独占的物理内存。这与 JS 堆约 1–2MiB 是完全不同的口径。

### 专业判断

日常几十到几百项任务、单窗口的桌面日程工具，当前响应速度、后台 CPU 和有上限的花丛结构可以接受。约 108MiB 的私有驻留体现了 WebView 运行时和界面的常驻成本，暂停动画不会让它变成几 MiB。

750 项全部展开时约 204MiB 的私有驻留偏高，应将任务列表的按需挂载/视口化作为后续内存优化重点。该压力场景并未增加花丛数量，不能把全部增长归因于花丛。当前没有长期、多窗口、集显或电池功耗数据，不据此承诺所有机器和窗口数量都能保持相同占用。
